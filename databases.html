Раздел 3

Базы данных: как сайт запоминает информацию

Пользователи, задачи, товары, комментарии — всё, что должно сохраниться после закрытия вкладки, хранится в базе данных. Разберём SQL на примере SQLite и покажем, как то же самое делает ORM в Django.

Зачем серверу база данных

Переменные в Python живут, пока работает программа. База данных хранит данные на диске и умеет быстро их находить.

🗂️Таблицы

Данные лежат в таблицах: строка — одна запись (товар), столбец — одно свойство (название, цена).

🔑Первичный ключ

У каждой строки есть уникальный номер id. По нему запись можно найти, изменить или удалить.

💬SQL

Язык запросов к базе: SELECT читает, INSERT добавляет, UPDATE меняет, DELETE удаляет.

🧩ORM

Прослойка, которая превращает классы Python в таблицы, а вызовы методов — в SQL-запросы.

SQL на практике: модуль sqlite3

SQLite — база данных в одном файле. Она встроена в Python, сервер для неё не нужен, поэтому это лучший вариант для учебных проектов. Сохраните код в файл и запустите — он создаст shop.db.

shop.py 
import sqlite3

conn = sqlite3.connect("shop.db")

conn.execute("""
    CREATE TABLE IF NOT EXISTS products (
        id INTEGER PRIMARY KEY,
        name TEXT NOT NULL,
        price INTEGER NOT NULL
    )
""")

conn.execute("INSERT INTO products (name, price) VALUES (?, ?)", ("Тетрадь", 350))
conn.execute("INSERT INTO products (name, price) VALUES (?, ?)", ("Ручка", 150))
conn.commit()

for name, price in conn.execute("SELECT name, price FROM products WHERE price < ?", (300,)):
    print(name, price)  # Ручка 150

conn.execute("UPDATE products SET price = ? WHERE name = ?", (400, "Тетрадь"))
conn.execute("DELETE FROM products WHERE name = ?", ("Ручка",))
conn.commit()

print(conn.execute("SELECT name, price FROM products").fetchall())  # [('Тетрадь', 400)]
conn.close()

Не забывайте commit(). Изменения (INSERT, UPDATE, DELETE) попадают в файл только после вызова conn.commit(). Без него данные пропадут при закрытии соединения.

Главное правило безопасности: параметры вместо f-строк

Если вставить текст пользователя прямо в SQL, пользователь сможет изменить сам запрос. Это называется SQL-инъекцией — одна из самых частых уязвимостей сайтов.

Опасно: f-строка 
name = "' OR '1'='1"  # так может ввести пользователь

rows = conn.execute(
    f"SELECT * FROM products WHERE name = '{name}'"
).fetchall()
# вернутся ВСЕ товары: условие стало всегда истинным
Безопасно: параметр ? 
name = "' OR '1'='1"

rows = conn.execute(
    "SELECT * FROM products WHERE name = ?", (name,)
).fetchall()
# вернётся пустой список: товара с таким названием нет

То же самое через ORM Django

В Django таблицу описывают классом-моделью, а запросы пишут методами Python. SQL Django составляет сам и всегда подставляет значения как параметры — инъекция здесь не страшна.

shop/models.py 
from django.db import models

class Product(models.Model):
    name = models.CharField(max_length=100)
    price = models.PositiveIntegerField()
python manage.py shell 
from shop.models import Product

Product.objects.create(name="Тетрадь", price=350)
Product.objects.create(name="Ручка", price=150)

cheap = Product.objects.filter(price__lt=300)  # Ручка
Product.objects.filter(name="Тетрадь").update(price=400)
Product.objects.filter(name="Ручка").delete()
Одни и те же операции на SQL и в ORM Django
Действие SQL ORM Django
Добавить INSERT INTO products (name, price) VALUES (?, ?) Product.objects.create(name=…, price=…)
Найти по условию SELECT … FROM products WHERE price < 300 Product.objects.filter(price__lt=300)
Изменить UPDATE products SET price = 400 WHERE … Product.objects.filter(…).update(price=400)
Удалить DELETE FROM products WHERE … Product.objects.filter(…).delete()

Миграции: как модель становится таблицей

Миграция — файл с инструкцией «как изменить базу». Django создаёт его по изменениям в моделях, а затем применяет. Так структура базы всегда совпадает с кодом, и её легко повторить на другом компьютере.

Терминал 
python manage.py makemigrations   # создать миграцию по моделям
python manage.py migrate          # применить её к базе
python manage.py sqlmigrate shop 0001   # показать SQL миграции
SQL, который сгенерировал Django 
CREATE TABLE "shop_product" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    "name" varchar(100) NOT NULL,
    "price" integer unsigned NOT NULL CHECK ("price" >= 0)
);

Обратите внимание: PositiveIntegerField превратился в проверку CHECK ("price" >= 0) — база сама не даст сохранить отрицательную цену. Вывод получен командой sqlmigrate на Django 6.1 и SQLite.

Какую базу выбрать

Код с ORM почти не меняется при смене базы — меняются настройки подключения.

Популярные базы данных для Python-проектов
База Когда использовать Особенности
SQLite Учебные проекты, прототипы, небольшие сайты Один файл, встроена в Python, база по умолчанию в Django
PostgreSQL Реальные проекты с пользователями Отдельный сервер, надёжная работа при одновременных запросах
MySQL / MariaDB Когда её предоставляет хостинг Отдельный сервер, распространена на хостингах

Во Flask своей ORM нет. Можно писать SQL через sqlite3, как во втором шаге проекта на Flask, или подключить расширение Flask-SQLAlchemy.

Проверь себя

Четыре вопроса по разделу. После ответа появится объяснение.

1. Какая команда SQL изменяет уже существующие записи?

UPDATE меняет существующие строки, INSERT добавляет новые, SELECT только читает.

2. Как безопасно подставить ввод пользователя в запрос sqlite3?

Параметры передаются отдельно от текста запроса, поэтому ввод пользователя не может изменить SQL. F-строка и сложение строк открывают дорогу SQL-инъекции.

3. Вы добавили поле в модель Django. Что нужно сделать, чтобы изменилась таблица?

makemigrations создаёт файл миграции по изменениям модели, migrate применяет его к базе. Удалять базу не нужно — данные сохранятся.

4. Почему изменения в sqlite3 могут не сохраниться?

Изменяющие запросы выполняются в транзакции и записываются в файл только после commit().
